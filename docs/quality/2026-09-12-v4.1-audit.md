# v4.1.0 Reliability Audit and Delivery Plan

Audit date: 2026-09-12. This is a findings and implementation plan, not a release announcement or a claim that every feature is error-free.

## Scope and Release State

The public web release remains **v4.0.1**. `main` and fetched `origin/main` both pointed to `db1c56b` during this audit, with zero commits ahead or behind. The working tree also contains unreleased MagnetAPI, model-label, banner, and application-shell changes. Those changes were preserved; they are not proof of deployment.

The audit traced the six-module prompt, provider, runtime, persistence, account, and route boundaries. Chromium exercised production pages, a local production build, and actual hosted FREE generation on `alpha1.bolt.gives`. Small isolated fixtures exercised runtime contracts without changing production database configuration. No customer workspace was edited, no live Stripe payment was taken, and no fleet deployment or Windows release was performed.

The next web target is **v4.1.0: reliability first**. The released Windows line remains **Desktop v1.10.2**. A native rewrite has its own release decision and must not inherit the web version number.

### Real Project Evidence

Using an audit-only profile created through the normal UI, Chromium submitted a task-board prompt through hosted FREE. No onboarding overlay was removed or bypassed with JavaScript.

The second run reached its requested first Preview in approximately **99 seconds**, added a fourth task through the generated application's button, applied a follow-up subtitle in approximately **92 seconds**, and restored that updated Preview after reload. The restored conversation displayed the follow-up and the composer remained visible. The recorded chat requests contained three then five messages. These are single-run observations, not latency guarantees.

The first run also reached Preview, but a Code-to-Preview interaction timed out. The second run recorded a snapshot HTTP 502, an aborted signal, and a snapshot exception despite eventually displaying the correct app. Therefore **the functional journey succeeded, but the clean E2E release criterion did not**. Sidebar project switching, browser restart, runtime restart, and publication were not verified in this run.

Local, ignored evidence is under `output/playwright/audit-20260912/` and `output/playwright/audit-20260912-rerun/`: route measurements, contract results, generation stages, and screenshots. These are local audit artifacts, not public release assets. Do not publish raw browser storage, HARs, cookies, or customer snapshots when promoting evidence to CI. The temporary local app and the two owned audit Preview processes were stopped after testing; source/history were retained. No shared service was restarted for cleanup.

## Confirmed Findings and Small Fixes

P1 blocks reliable use, account isolation, or release confidence. P2 is a material usability or truthfulness defect. Each numbered subtask below should be an independently reviewable change with regression coverage, normally one focused PR rather than a module rewrite.

### B01: Package Caches Enter Source Snapshots - P1

**Reproduced live and in an isolated fixture.** The audit project's snapshot included thousands of package-cache/store entries. A tiny local fixture also included `.cache`, `.local`, and nested `node_modules`; `.github` was correctly retained. These trees can inflate transport, editor, history, and model-context work. They are a plausible contributor to the observed lag, not yet a proven explanation for every timeout.

Owner: runtime, with project/core consumers. Trace: [runtime snapshot walker](../../scripts/runtime-server.mjs), `PRESERVED_DIRS`, `walkWorkspace`, and `buildWorkspaceFileMapFromDisk`.

1. B01a: Establish a shared source-path policy applied at every directory depth, including cached snapshot reads and browser reconciliation. Exclude machine-local/build trees while retaining real hidden source. Test nested dependencies, caches, `.github`, symlinks, and legitimate assets.
2. B01b: Add bounded snapshot file count, total bytes, per-file reads, and cancellation. Do not read a whole binary into memory merely to apply a later limit. Measure payload, heap, and editor responsiveness before/after on the same fixture; reject excessive input with an explicit error.

### B02: Same-Count Disk Changes Can Return Stale Source - P1

**Reproduced in an isolated fixture.** `resolveSessionSnapshotFiles` preferred in-memory content when disk had the same file count and neither version contained a starter placeholder. Changing a file's contents on disk returned the old in-memory text. The file-count heuristic also needs deletion and rename coverage.

Owner: runtime/project. Trace: [snapshot selection](../../scripts/runtime-server.mjs), `resolveSessionSnapshotFiles`.

1. B02a: Replace file-count freshness with a versioned reconciliation rule that detects changes, renames, and deletions without overwriting concurrent model writes. Test external CLI edits and equal-size/equal-count replacements.
2. B02b: Prove that saved source, editor, follow-up context, and Preview use the same revision after reload and runtime restart. Preserve the last healthy snapshot and report persistence failures rather than silently using stale files.

### B03: Pricing Returns HTTP 500 - P1

**Reproduced in Chromium on production and the local build.** Direct navigation to `/pricing` renders “Application Error” on desktop and phone. [The pricing route](../../modules/surfaces/app/routes/pricing.tsx) directly renders an export from `BillingUpgradeButton.client`; its SSR boundary is the first code path to isolate, not an excuse to hide the exception.

Owner: surfaces/control-plane.

1. B03a: Reproduce the server-render failure in a route test and make the upgrade control SSR-safe. Require direct GET and in-app navigation to render the actual pricing content with HTTP 200.
2. B03b: Test the real Upgrade-to-login-to-Checkout return path with Stripe test mode. Cover cancellation, retry, double clicks, and a disabled billing configuration; also verify that the restored pricing page has a reachable vertical scroller.

### B04: Database-Free Self-Host Cannot Finish Onboarding - P1

**Reproduced at the isolated runtime boundary and verified against the UI contract.** Without platform database configuration, registration returns HTTP 503: “Profile storage is not configured on this server.” The mandatory [profile dialog](../../modules/surfaces/app/components/profile/ProfileOnboarding.tsx) has no corresponding self-host path. The installer now leaves PostgreSQL off by default, so a healthy service can still block first use.

Owner: control-plane/surfaces and installer integration. Trace: [runtime profile registration](../../scripts/runtime-server.mjs), `/runtime/profile/register`, and [installer](../../install.sh).

1. B04a: Expose platform-auth capabilities explicitly. Provide a local, single-user self-host mode when profile storage is absent, or an explicit configured external identity path. Do not weaken hosted authentication, quotas, or multi-user ownership.
2. B04b: Run a clean no-database Ubuntu install through first prompt, Preview, follow-up, and reload. Separately test `--with-postgres`. Installation success must include a usable onboarding path, not only listening services.

### B05: Provider Credentials Are Not Cleared on Logout - P1

**Reproduced with a dummy sentinel, never a real key.** The provider cookie remained after logout. [API-key storage](../../modules/agent/src/lib/runtime/api-key-storage.ts) is origin-wide, while [logout](../../modules/surfaces/app/routes/logout.ts) clears the profile session. The normal key-loading path is not profile-scoped.

Owner: agent/control-plane/surfaces.

1. B05a: Define account-owned credential storage and clear in-memory, cookie, and recoverable browser copies on logout/account change. Address legacy-key migration explicitly; do not transfer a previous user's keys to a new account.
2. B05b: Use dummy keys in a two-profile, two-tab regression. Assert that logout and login never reuse another profile's credential, including delayed secure-storage loads. Keep operator-funded FREE and user-funded MagnetAPI credentials separate.

### B06: Unreachable Supabase Is Labelled Connected - P2

**Reproduced in an isolated fixture.** Saving an unreachable `.invalid` project URL with a dummy key returned `status: connected`. [Connection persistence](../../modules/runtime/src/server/project-connections.mjs) verifies PostgreSQL but only validates the shape of Supabase settings; [the UI](../../modules/surfaces/app/components/chat/SupabaseConnection.tsx) reports a successful connection.

Owner: runtime/surfaces.

1. B06a: Separate saved/configured, verifying, reachable, authentication-failed, and unavailable states. Implement a bounded, safe probe that respects Supabase public-key/RLS semantics; do not treat an empty table or restrictive RLS as failed credentials.
2. B06b: Test incorrect URL/key, timeout, rotation, disconnect, and a subsequent Preview start. Keep private connection records out of source and static PostgreSQL deployment artifacts; explain when already-running processes need restarting.

### B07: Login Is Clipped in Short Windows - P2

**Reproduced at 390x500.** The submit button's bottom was at approximately 646px; mouse-wheel scrolling did not move either the window or main content. [Login](../../modules/surfaces/app/routes/login.tsx) combines `min-h-screen`/`overflow-hidden` with the globally non-scrolling body.

Owner: surfaces.

1. B07a: Give login an explicit available-height scroller that accounts for dismissible banners and mobile keyboards. Keep the submit button and feedback reachable.
2. B07b: Add keyboard, short-window, phone, 200% zoom, and banner-visible/dismissed checks to the route suite.

### B08: Onboarding Does Not Contain Keyboard Focus - P2

**Reproduced in Chromium.** With the mandatory dialog visible, Tab focused the underlying banner, header, sidebar, and model controls rather than remaining in the form. `aria-modal` alone does not implement focus management.

Owner: surfaces. Trace: [ProfileOnboarding](../../modules/surfaces/app/components/profile/ProfileOnboarding.tsx).

1. B08a: Use the established accessible dialog primitive with initial focus, focus containment, background inertness, and a deliberate dismissal policy. Required hosted onboarding must still have a reachable login option.
2. B08b: Verify forward/backward tab order, focus restoration, screen-reader labels/errors, high contrast, and full scrolling on small screens.

### B09: Payment Confirmation Trusts a Query String for Its Message - P2

**Source-verified; browser confirmation is blocked by B03.** The [pricing page](../../modules/surfaces/app/routes/pricing.tsx) says “Payment received” whenever `billing=success` is present. This finding concerns misleading messaging, not a demonstrated entitlement bypass.

Owner: control-plane/surfaces.

1. B09a: Render pending/confirmed payment status from authenticated server-side billing state. A return URL alone must not assert payment receipt.
2. B09b: Cover forged success parameters, delayed/duplicate webhooks, failed renewal, cancellation, and refresh. Only signed, idempotent billing events may change entitlements.

### B10: Commentary Contradicts Completed Runtime State - P2

**Observed in the real browser journey.** A restored app displayed “Ready / Build” and “Preview ready” while commentary still showed “Active” and waited for another checkpoint. During generation, repeated generic “next command or file event” text obscured concrete changes.

Owner: agent/surfaces. Trace: [CommentaryFeed](../../modules/surfaces/app/components/chat/CommentaryFeed.tsx) and [commentary heartbeat](../../modules/agent/src/lib/runtime/commentary-heartbeat.ts).

1. B10a: Derive a single terminal/working/recovering state from actual run, command, persistence, and Preview events. Reconstruct the correct terminal state when loading history.
2. B10b: Replace generic progress filler with real active-operation status, bounded recovery outcomes, and useful next actions. Test reconnect/reload and event ordering; verify text contrast and prevent layout flashing.

### B11: Release Checks Can Miss Broken User Journeys - P1

**Source-verified test defects.** [Release gate](../../scripts/release-gate.mjs) checks versions/screenshots while explicitly skipping prompts. [Preview recovery E2E](../../scripts/e2e-preview-auto-recovery.mjs) still expects a removed Workspace tab and old prompt placeholder. [Calendar E2E](../../scripts/e2e-calendar-build.mjs) makes follow-up and history checks opt-in. Current installer smoke does not run an OS installation.

Owner: surfaces/project plus release tooling.

1. B11a: Update fixtures for normal profile onboarding and v4 Agent Mode. Never use `element.click()` behind an overlay as evidence that a user can access a control. Make functional failures and unexpected server/browser errors fail the process.
2. B11b: Make first Preview, interaction, follow-up, same-project history, Code selection, route status, and bounded recovery mandatory release checks. Add real Ubuntu clean/repair jobs separately; keep fast unit tests as the inner loop.

### B12: Browse Fallback Has a Weaker Network Validation Contract - P1

**Source-verified risk; no private-network probing was performed.** [The fetch fallback](../../modules/surfaces/app/routes/api.web-search.ts) validates the initial URL with [a hostname/literal check](../../modules/core/src/utils/url.ts), then uses ordinary redirect-following fetch. This is not the same as validating resolved destinations and every redirect hop.

Owner: core/agent/surfaces.

1. B12a: Share a fail-closed public-destination policy across browser and fetch transports, including redirects, IPv4/IPv6, resolution changes, content-size limits, deadlines, and redacted failures.
2. B12b: Use controlled local test doubles for blocked destination and redirect cases, plus a public-page browse-to-build test. Do not test against real private services or publish sensitive infrastructure details.

## Native Windows Rewrite

### Technical Direction

Use **C++20, C++/WinRT, WinUI 3/XAML, and the Windows App SDK** as the preferred implementation, built and tested on Windows. Microsoft documents WinUI 3 as its recommended native framework for new Windows apps and supports both C++ and C#: [Windows development paths](https://learn.microsoft.com/en-us/windows/apps/get-started/).

The existing WPF client is already a Windows-native technology. Rewriting it in C++ is not, by itself, a performance fix. First prove editor/terminal interoperability, accessibility, startup, memory, and update migration in a small vertical slice. C# with WinUI 3 is the fallback only if that measured spike shows a materially safer implementation; record the decision before expanding the rewrite.

Use native controls for login, projects, conversation, composer, editor, terminal, settings, billing/deployment status, and updates. **No Electron, hosted-product iframe, or web UI wrapper.** WebView2 is restricted to the user's generated application Preview. Desktop v1.11.0 supersedes the audit's former private-source assumption: source and CI now live under `desktop/windows`, while signing credentials and runtime secrets remain private. Work on bolt.gives; the separately developed commercial product is out of scope.

The normal application must not run elevated. Request elevation only if the selected installation scope needs it. Respect Windows consent for taskbar pinning. Mandatory update policy must be authenticated and support a tested recovery route; do not force an upgrade to an unverified binary or promise that failures are impossible. Resolve the existing public-signing-trust requirement before claiming a warning-free installation.

Proposed release identity: **Desktop v2.0.0**, subject to migration/parity results. Continue supporting v1.10.2 until the replacement passes W07. Web v4.1.0 can ship verified web fixes independently; do not label an incomplete Windows rewrite as part of a completed web release.

## Execution Order and Release Exit

1. Fix B03/B04/B05 first for access and account safety; begin B01/B02 in the runtime lane and B12 in the browse lane. Add the failing tests before their fixes.
2. Complete B06-B10, then use B11 and I01-I06 to prove cross-module behavior and installer readiness. Do not add unrelated feature scope.
3. Run W01/W02 in the private Windows lane, approve the measured stack/packaging decision, and then execute W03-W07 against the stabilized server contracts.
4. Run boundaries, typecheck, lint, tests, build/bundle budgets, and a mandatory real-browser release journey. A successful screenshot or HTTP 200 alone is insufficient.
5. Require zero unresolved P1 findings, no unexplained browser/5xx errors, no stale account data, and clean first-pass/follow-up/restore/Code-selection evidence on alpha1 plus one disposable managed instance. Resolve P2s or explicitly defer them with an owner, workaround, and rationale before approval.
6. Establish repeatable performance budgets from the audited fixture before optimizing: measure snapshot bytes, idle polling, input latency, long tasks, heap, Preview startup, and follow-up latency on a named machine/network/provider. Enforce non-regression in CI rather than claiming competitor-level speed from a single run.
7. Only then align version, changelog, README, tags, artifacts, deployed manifests, and staged fleet health. Keep a known-good rollback; publish Windows artifacts only after its independent gate.

Contributors can claim one B/I task through [Issues](https://github.com/embire2/bolt.gives/issues) or discuss the plan in [the existing feature thread](https://github.com/embire2/bolt.gives/issues/6). Use private security reporting for sensitive findings and omit credentials/customer data from all reports.
